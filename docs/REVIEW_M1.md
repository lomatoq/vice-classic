## 3. Проверка gate по существу

Ниже — не пересказ STATUS, а мои собственные измерения. Для проверки я
собрал **отдельный crate** (`%TEMP%\m1adv`), зависящий от `vice-ir`/`vice-geom`
по path, и строил сцены только через публичный API, не переиспользуя
авторский `tests/common/mod.rs`. Это важно: авторские негативные тесты
строятся тем же builder-ом, что и позитивные, поэтому независимый builder —
единственный способ не унаследовать его слепые зоны.

### (a) Property roundtrip: canonical bytes → parse → re-serialize побайтово

Подтверждено, и существенно шире авторского набора:

- **256/256 цветов вида `k/255`** проходят roundtrip побайтово, включая
  `23/255 = 0.09019607843137255` — ловушку F-0005 (см. §5).
- Тяжёлые f64: `1/3`, `f64::MIN_POSITIVE`, `f64::MAX`, денормаль `5e-324`,
  `0.1+0.2` — либо побайтовый roundtrip, либо typed reject до сериализации.
  Ни одного случая «сериализовалось, но не вернулось».
- `PROPTEST_CASES=3000` на всех семи свойствах — зелено (по умолчанию 256).
- Golden-файл: я **независимо** пересчитал sha256 по закоммиченным байтам
  своей реализацией →
  `112d0478f86b57ca94bb8d1805042894ce2e1da640297f119853fca61cc2f1f9`,
  совпало с замороженной константой в `golden_digest.rs`. Повторный parse
  golden-файла даёт те же байты.

Строгость парсера проверена мной отдельно (все — reject):

| Атака | Результат |
|---|---|
| лишнее поле `vertices_extra` внутри графа | `Json("unknown field ...")` |
| дублированный ключ `schema` | `Json(...)` |
| `"x":"NaN"` (строкой) | `Json("invalid type: string")` |
| `"x":NaN` (голый литерал) | `Json("expected value")` |
| `"x":-0.0` | `Invalid(NegativeZero { location: "vertices[0].pos.x" })` |
| `"g":-0.0` в paint | `Invalid(NegativeZero { location: "faces[1].paint.g" })` |
| `"x":1e999` | `Json("number out of range")` |
| `schema = vice-classic/scene/v2` | `SchemaMismatch` |
| усечённые байты (1..64 байт с конца) | reject (property, 3000 кейсов) |

Два случая **корректно НЕ отвергаются**, и это правильное поведение, а не
дыра:

- **переставленные ключи** JSON — парсятся, и `canonical_scene_bytes`
  возвращает те же байты и тот же digest. Канонизация переносит альтернативную
  кодировку в канон — ровно то, ради чего она существует;
- **`"x":8` вместо `"x":8.0`** — то же самое, digest совпадает.

Контроль на чувствительность: сдвиг одной координаты на 1 ulp
(`8.0 → 8.000000000000002`) даёт **другой** digest. Канон не «съедает»
семантические изменения.

### (b) Same-platform byte determinism, включая независимость от порядка построения

Подтверждено четырьмя независимыми способами:

1. **Полная реверсивная перенумерация** всех четырёх entity-векторов
   (вершины, boundaries, half-edges, faces) с ремапом всех ссылок, включая
   перенос exterior-face из индекса 0 в конец → **те же байты, тот же digest**.
2. **Ротация представителя loop-а**: заменил каждый `Face.loops[i]` на
   `next(loops[i])` (другой half-edge того же цикла) → те же байты.
3. **100 повторных сериализаций** одной сцены в одном процессе → идентичны.
4. **Debug и release** дают одинаковые golden-байты; два процесса, две
   конфигурации оптимизации, один результат.

Дополнительно я проверил **доказуемость**, а не только эмпирику. Канонический
порядок тотален тогда и только тогда, когда ключи сортировок уникальны:

- вершины сортируются по `lex_cmp` позиции → ничьи исключены reject-ом
  `DuplicateVertexPosition`;
- boundaries — по `(start', end', JSON кривой)` → ничьи исключены reject-ом
  `DuplicateBoundary`;
- half-edges нумеруются как `2b + !forward` → биекция обеспечена проверкой
  «ровно один forward и один reverse на boundary»;
- faces — по отсортированным loop-ключам; ключи разных faces дизъюнктны, так
  как пара `(boundary, forward)` принадлежит ровно одному half-edge → одному
  циклу → одному face, а face без loops отвергается.

То есть детерминизм здесь не «повезло с сортировкой», а следствие
валидации. `sort_by` (стабильная) нигде не может дать порядок-зависимый
результат. Это сделано правильно и продумано.

Отдельно отмечу инженерное решение, которое действительно работает: shared
parameters структурно неповторимы. В golden-файле boundaries содержат только
`start_vertex`/`end_vertex` (id), позиции лежат только в таблице вершин,
interior-узлы и shared tangent — по одному экземпляру. «Проквантовать
общий параметр дважды по-разному» непредставимо, а не «запрещено правилом».

### (c) Invalid graphs rejected — покрытие инвариантов §12

Качество авторских негативных тестов высокое: каждый assert проверяет
**конкретный вариант typed-ошибки** (`GraphError::EulerMismatch { v:1, e:3,
f:2, c:1 }`), а не просто `is_err()`. Это дороже писать и сильно труднее
подделать.

Сопоставление со списком §12:

| Инвариант §12 | Проверяется | Как |
|---|---|---|
| каждый half-edge имеет twin | да | `TwinViolation` (self-twin, неинволютивность, другая boundary, то же направление) |
| каждая interior boundary имеет два owners | да | ровно один forward + один reverse (`BoundaryHalfEdgeCover`) |
| border boundary = interior + exterior owner | да | следует из `left ≠ right` + exterior как обычный face + face-side consistency |
| face cycles замкнуты и ориентированы | комбинаторно — да; геометрически — нет | `next` — перестановка, `target(h)=origin(next(h))`, циклы не смешивают faces, `Face.loops` = ровно один представитель на цикл |
| no dangling cracks | да | `DanglingCrack` (`left == right`) |
| Euler/сигнатура сохранена | да | `V − E + F = 1 + C` через union-find |
| non-adjacent boundaries не пересекаются | **частично — см. M1-N1** | точно для line-line; кривые — bbox-сертификат либо явный UNDETERMINED-worklist |

**Euler-проверка — сильное место.** Она не декоративна. Формально: число
орбит `next` равно `O`, каждый face обязан иметь ≥1 loop и loops дизъюнктны,
значит `F ≤ O`; для связного вложения рода `g` верно `V−E+O = 2−2g`, а
требуемое `F = 2−V+E = O+2g`. Из `F ≤ O` следует `g = 0`. То есть проверка
**доказуемо** отвергает непланарные rotation systems, а не ловит их
эвристически. Авторский тест «тор из трёх петель» — корректная демонстрация.

### Сужение объёма: `SceneHypothesis` и провенанс-типы — собственное суждение

Это ключевой спорный пункт, и я обязан вынести по нему решение сам.

**Что заявляет автор** (ADR-0005 п.5, `lib.rs`, STATUS_M1 §1): `SceneHypothesis`,
`EvidenceRef`, `SupportRef`, `SceneProvenance`, `DecisionInterval`, `ExportPlan`
сознательно не созданы, потому что в M1 у них нет ни одного producer/call site,
а §32 п.7 и §4.1 это запрещают.

**Что говорит spec.** §28 M1 перечисляет среди пунктов «geometry/paint/
formation/**hypothesis types**». Одновременно §4.1 требует буквально: «не
писать placeholder traits/APIs для M5–M12 во время M0–M4», «не вводить
abstraction, пока нет как минимум двух реальных implementations/call sites»;
§32 п.7 — «No placeholder crates/APIs». **Gate** же §28 M1 сформулирован
исчерпывающе и не упоминает hypothesis-типы вовсе: «property roundtrips,
same-platform byte determinism, invalid graphs rejected».

**Моё решение: сужение законно.** Аргументы, в порядке весомости:

1. Все поля `SceneHypothesis` из §6.3 (`posterior_bits`, `lower_bound_bits`,
   `delivery_class`, `topology_id`, `formation_id`, `grammar_id`,
   `certificates`) ссылаются на сущности, которых не существует и не может
   существовать в M1. Созданный сейчас `SceneHypothesis` был бы не «типом», а
   пустой оболочкой из шести не-типов — то есть буквально placeholder API для
   M5–M7, прямо запрещённый §4.1.
2. Сам §6.3 привязывает семантику этих типов к M5+ («M5 не имеет права
   назвать topology окончательным winner…»), а §5.4 привязывает
   `DecisionInterval` к первому производителю score. В M1 score-ов нет ни
   одного.
3. Gate M1 — нормативная часть — не содержит hypothesis-типов. Пункт списка
   выше gate — эскиз объёма, и при прямом конфликте с явным запретом §32/§4.1
   выигрывает запрет.
4. Автор **не** обнулил пункт целиком: `GlobalFormationHypothesis` —
   настоящий hypothesis-тип из §6.1, он создан, провалидирован, сериализуется
   и входит в canonical bytes и digest. То есть «hypothesis types» в M1-объёме
   поставлены, а отложена именно M5+-часть.
5. Отказ задокументирован в трёх местах (`lib.rs`, ADR-0005 п.5, STATUS_M1) и
   занесён в `REQUIREMENTS_TRACEABILITY.md` строкой M1-5 — он не может тихо
   исчезнуть.

**Ремарка о последовательности принципа.** Тем же тестом «нет call site»
можно было бы срезать `connectivity.rs` и половину `color.rs`
(`LinearRgba`/`PremulRgba`/`premultiply`/sRGB transfer): в M1 у них тоже нет
продакшн-потребителя, только тесты. Автор их оставил — и правильно, потому
что §28 M1 называет «coordinates/color/topology conventions» прямым
deliverable-ом милестоуна. Граница проведена по признаку «принадлежит ли
семантика типа этому милестоуну», а не «есть ли call site», и это
последовательно. Но формулировку в ADR-0005 стоит уточнить, чтобы принцип не
выглядел применяемым избирательно.

**Обязательное следствие (не блокирует M1).** Первый милестоун, который
породит posterior/score/evidence, обязан ввести соответствующий тип **вместе**
с его producer-ом, а `REQUIREMENTS_TRACEABILITY.md` — сохранять строку об
отложенных типах до момента их появления.

### PORTING_MANIFEST — 0 units и проверка на скрытое копирование

`PORTING_MANIFEST.toml` по-прежнему содержит **ноль** `[[unit]]`; вместо них
записаны три reference-only кандидата с явной пометкой, что до license-grant
из них копировать нельзя.

Я провёл **независимую сверку с донорами** (`v-ice`, `v-ize`, `v-ice part`,
последний подтверждён как клон `lomatoq/Vice-` ровно на пине `200897ab`;
сравнение велось в том числе с версиями файлов на пинах, а не только с HEAD):
n-gram-скан всех 12 новых исходников против всех Rust-файлов обоих Rust-доноров
и 149 Python-модулей третьего, с последующим ручным чтением каждого файла с
пересекающейся ответственностью.

**Вывод: следов копирования нет; «0 ported units» достоверно.** Ключевые
основания:

- `predicates.rs` — копировать было **не из чего**: grep по всем трём донорам
  на `orient2d|incircle|Shewchuk|robust =` даёт ноль совпадений. Ни один донор
  не содержит exact-предикатов и не зависит от `robust`.
- `vec2.rs` — единственный файл с заметным пересечением (~9% 8-грамм с
  `v-ize/crates/vize-core/src/geom.rs`), и всё пересечение — это блоки
  `impl Add/Sub/Mul<f64>/Neg` и однострочный `dot`, которые в Rust
  записываются единственным способом. Наборы методов расходятся почти
  полностью: у донора `len/len2/normalized/deriv/eval/#[inline]/Default`, у
  цели — `ZERO/const fn new/AddAssign/SubAssign/dist_sq/is_finite/
  has_negative_zero/lex_cmp` + serde + 50 строк тестов, ничего из этого у
  донора нет.
- `color.rs` — совпадает ровно текст формулы sRGB IEC 61966-2-1 (`/12.92`,
  `((e+0.055)/1.055).powf(2.4)`), которая внутри самого донора встречается
  четырежды, потому что это константа стандарта. Назначение противоположное:
  все донорские варианты — `f32`, от `u8`, и существуют исключительно ради
  Oklab/CIELab; в цели нет ни строки Oklab, зато есть обратная функция и пара
  `premultiply`/`unpremultiply`, которых у доноров нет вовсе.
- `graph.rs`/`validate.rs` — цель спроектирована **против** донора, а не из
  него: донорский `vice_scene/topology.py` объявляет `OUTSIDE = -1`, а
  `graph.rs` в первых строках фиксирует «настоящий FaceId, а не отрицательный
  magic label». Донорский `HalfEdge` — граф смежности пиксельных регионов без
  `next`, `face` и loops. Grep на `euler` по всем донорам — ноль совпадений.
- `canonical.rs` — у доноров есть только generic-идиома
  `json.dumps(..., sort_keys=True) + sha256` для манифестов файлов; ничего
  похожего на permutation-invariant канонизацию графа не существует.
- `curve.rs` — донорский `Seg` хранит endpoints в каждом варианте и
  центр-угловую параметризацию дуг; цель хранит endpoints **вне** сегмента и
  использует SVG-endpoint-параметризацию. Противоположный design intent.

Два честных ограничения этого вывода, которые я фиксирую явно: (1) все
репозитории принадлежат одному автору, поэтому «независимость» отчасти
неотличима от привычек кодирования — но совпадающие фрагменты не являются
охраноспособным выражением; (2) «clean-room» здесь означает «код не копировался»,
а не «доноры не были известны» — и это ровно то, что заявлено, поскольку сам
манифест открыто перечисляет донорские файлы как reference-only.

Побочно подтвердилось, что путь `lomatoq/v-ice src/core/geom.rs` в манифесте
**корректен на пине** (`9211b32…`), хотя не совпадает с текущим рабочим
деревом донора. Автор работал против пина; манифест точен.

Вендоринга нет: каталогов `vendor/`/`third_party/` нет, `.cargo/config` с
source replacement нет, `robust` подключён как обычная зависимость.

### Hidden env flags (§32 п.4)

Полный grep по `crates/` на `std::env::var|env::var|option_env!` даёт ровно
три вхождения, и ни одно не является скрытой ручкой поведения:

1–2. `envinfo.rs:56,61` — `env::var_os(name).is_some()`: читается **только
факт присутствия** переменной, для записи имени в отчёт. Значения не
читаются и не пишутся (авторский тест это проверяет; я подтвердил
независимо — при `RUSTFLAGS="--cfg reviewer_bogus"` в `env.json` попало имя
`RUSTFLAGS`, но не значение).

3. `baseline-runner.rs:248` — подкоманда `env-probe NAME OUT`, явный
тестовый адаптер: имя переменной приходит **обязательным CLI-аргументом**,
результат пишется в файл. Это инструмент наблюдения за санацией, а не канал
влияния.

Сама политика санации (`CHILD_ENV_REMOVE`/`CHILD_ENV_SET` в `exec.rs`) —
**константы в коде**, не конфиг и не env.

**Моя оценка: это соблюдение §32 п.4, а не нарушение.** Правило запрещает
скрытые переменные, меняющие *поведение*. Здесь поведение фиксировано
константой и неизменяемо извне, а чтение presence — противоположность
скрытости: оно делает ambient-загрязнение **видимым в отчёте**. Конструкция
превращает потенциальный скрытый канал (унаследованное окружение) в
задокументированный и захешированный факт. Правильное инженерное решение.

Оговорка о полноте применения политики — M1-N2.

## 5. Adversarial-проверки ревьюера

Всего исполнено ~25 сценариев; ниже — только те, что дали содержательный
результат. Все построены независимым от автора кодом.

### M1-N1 — **БЛОКЕР**: непредставленный junction принимается молча

**Что я сделал.** Построил две сцены, в которых две boundaries, **не имеющие
ни одной общей graph-вершины** (то есть non-adjacent в смысле §12),
геометрически касаются друг друга.

*Сцена C1.* Остров A — квадрат с вершинами `(10,10) (30,10) (30,30) (10,30)`.
Остров B — «линза» с graph-вершинами `(40,5)` и `(40,20)`; одна из её
boundaries — цепочка из двух отрезков с **interior-узлом ровно в `(30,10)`**,
то есть в углу острова A. `(30,10)` — graph-вершина A, но у B это не вершина,
а внутренний узел цепочки. Общих `VertexId` у этих boundaries нет.

```text
validate_scene                   → Ok(())
uncertified_interference_pairs   → 0 пар
scene_digest_sha256              → dc0a60cdfe90174f6653f95cf262471d6ee7a17bdad2a89cb6cb188d188aa4ab
```

*Сцена C4 (чище).* Два острова-линзы; у каждого одна boundary — цепочка из
двух отрезков, и **оба interior-узла находятся в одной точке `(20,15)`**,
которая не является graph-вершиной ни у одного из них.

```text
validate_scene                   → Ok(())
```

*Контроль C3.* Тот же узел сдвинут строго внутрь A (`(25,15)`) — касание
перестаёт приходиться на совпадающий узел:

```text
validate_scene → Err(Graph(BoundariesIntersect { a: BoundaryId(1), sa: 0,
                                                 b: BoundaryId(5), sb: 0 }))
```

То есть точный тест работает — он просто **не вызывается** для этого класса.

**Причина.** `crates/vice-ir/src/validate.rs:665`:

```rust
fn shared_points(a: &PrimSeg<'_>, b: &PrimSeg<'_>) -> Vec<Pt> {
    [a.p0, a.p1]
        .into_iter()
        .filter(|p| *p == b.p0 || *p == b.p1)
        .collect()
}
```

Смежность определяется **равенством ПОЗИЦИЙ** концов примитивных сегментов, а
не тождеством graph-вершин. Пара сегментов из non-adjacent boundaries,
совпадающих в одной точке, классифицируется как «adjacent» и в
`check_segment_interference` попадает в ветку `[s]`, где выполняется только
проверка коллинеарного перекрытия. Неколлинеарное касание не отвергается.
`uncertified_interference_pairs` использует ту же функцию (`if
!shared_points(a, b).is_empty() { continue; }`) и вдобавок безусловно
пропускает line-line пары как «decided exactly by validation» — поэтому пара
не попадает и в честный UNDETERMINED-worklist.

Тот же корень порождает и родственный случай: цепочка, у которой собственный
interior-узел совпадает с её же graph-вершиной через один сегмент
(самокасание), тоже принимается.

Дыра существует именно потому, что запрет дубликатов позиций
(`DuplicateVertexPosition`) распространяется **только на graph-вершины**;
interior-узлы цепочек под него не подпадают, хотя в DCEL любая точка, где
сходятся дуги, обязана быть вершиной.

**Почему это блокер, а не замечание.**

1. Это **прямое противоречие заявлению в gate-таблице**. STATUS_M1 §1 и G4
   утверждают: «пересечения non-adjacent boundaries: ТОЧНО для line-line пар».
   C1/C4 — line-line пары, non-adjacent, пересекающиеся, не отвергнутые.
   Я не могу подписать строку gate-таблицы, которую сам опроверг.
2. Это **не задокументированное ограничение, а расхождение кода с
   документацией**. ADR-0005 формулирует исключение как «Смежные (**с общей
   вершиной**) пары» — то есть по вершине. Код реализует «по совпадающей
   позиции». Grep по всем `.md` репозитория: слово junction/непредставленный
   стык нигде не упоминается. Known limitations STATUS_M1 покрывают кривые
   (п.1) и signed-area ориентацию loops (п.3) — этот случай не покрыт ни
   одним из них.
3. Это **невидимо для собственного механизма честности проекта**. Весь
   дизайн `uncertified_interference_pairs` построен на принципе «не доказано ≠
   безопасно». Здесь нарушение не отвергается **и** не регистрируется как
   неопределённое — единственный найденный мной случай, где система молчит.
4. **Последствия направлены вперёд.** §12 требует «robust junctions и border
   vertices». Валидатор M1 — это база, на которой M5 будет строить shared
   DCEL. Пропуск непредставленных стыков означает, что арранжировка M5 сможет
   их производить и проходить проверку, а Euler-подсчёт при этом считается по
   графу, который не является арранжировкой.

**Почему исправление дёшево (и почему REJECT здесь не карательный).**

- Я проверил golden-сцену на совпадающие точки: **14 вершин, 14 boundaries,
  16 различных позиций точек цепочек, 0 коллизий**. Ужесточение правила
  **не изменит** ни golden-байты, ни замороженный digest.
- Генератор property-тестов размещает острова в непересекающихся ячейках
  40×40, совпадений там тоже нет — property-корпус не пострадает.
- Ни один записанный артефакт (`docs/baselines/M0/**`) не затрагивается:
  правка только **добавляет** rejects.

**Минимальная требуемая правка (предлагаю, не навязываю форму).** Достаточно
любого из:

- (a) вести смежность по тождеству: `PrimSeg` уже знает свою boundary —
  считать пару смежной только если boundaries делят `VertexId`, а совпадение
  позиций у несмежных пар трактовать как пересечение; либо
- (b) ввести отдельный инвариант «все точки цепочек (graph-вершины +
  interior-узлы) попарно различны по позиции» — прямое обобщение уже
  существующего `DuplicateVertexPosition` на interior-узлы, с новым typed-вариантом.

Плюс негативные тесты на оба случая (C1 и C4) и уточнение формулировки в
ADR-0005 («общая graph-вершина», а не «общая точка»).

### M1-N5 — геометрическое вложение не проверяется (не блокер)

Сцена B2: остров 2 нарисован геометрически **внутри** острова 1, но
скоммутирован так, будто граничит с exterior. Проверено:

```text
validate_scene → Ok(())
digest         → c77661b27992016741adbf1c734d64da85fa5f1adf93837b0b194f1a7af49438
```

Все семь инвариантов §12 в буквальной формулировке выполнены: twins есть, у
каждой interior boundary два владельца, border-boundary имеет
interior+exterior владельца, циклы замкнуты и комбинаторно ориентированы,
dangling cracks нет, Euler `4−4+3 = 1+2` сходится, boundaries действительно не
пересекаются. Тем не менее планарного вложения не существует: exterior
оказался бы несвязным. Сцена B4 (перевёрнутая ориентация кольца) — тот же
класс.

**Вердикт: это НЕ gate-miss.** Список §12 выполнен буквально, а STATUS_M1
известное ограничение №3 честно фиксирует, что геометрическая ориентация
loops (outer vs holes по signed area) требует curve-машинерии и отложена.
Но зафиксировать надо жёстко: если это не станет hard-проверкой в M2,
формулировка «invalid graphs rejected» навсегда будет означать
«комбинаторно невалидные графы отвергаются».

### M1-N6 — геометрия вне canvas не валидируется (наблюдение)

Сцена с островом целиком за пределами `[0,W]×[0,H]` (квадрат в `(500,500)`
при canvas 96×96) валидируется как `Ok(())`. §12 такого инварианта не
содержит, и обрезка может быть легальной, поэтому это не дефект — но
политика должна быть выбрана осознанно в M2, когда появится renderer.
Отдельно проверил `canvas = u32::MAX × u32::MAX` — валидируется и
сериализуется без переполнений.

### Регрессия F-0005 — воспроизведена и подтверждена

`FAILURE_LEDGER.md` F-0005: дефолтный парсер `serde_json` читает f64 с
ошибкой до 2 ulp, из-за чего `parse → re-serialize` не побайтовый; поймано
gate-тестом на цвете `23/255`.

Проверил все три ноги:

1. **Фикс реально применён.** `crates/vice-ir/Cargo.toml:17`:
   `serde_json = { version = "1", features = ["float_roundtrip"] }`, с
   комментарием, объясняющим почему.
2. **Ловушка воспроизведена в моём коде.** Все 256 значений `k/255`
   проходят roundtrip побайтово; литерал `0.09019607843137255` присутствует в
   canonical-байтах и возвращается тождественно.
3. **Регрессия закреплена seed-ом.** Файл
   `crates/vice-ir/tests/canonical_props.proptest-regressions` закоммичен и
   содержит именно сжатый падавший кейс — сцену с
   `LinearRgb { r: 0.0, g: 0.0, b: 0.09019607843137255 }`. Proptest
   перепрогоняет его перед любыми новыми кейсами.

Это образцовая работа с отказом: правило выведено общее («любой парсер на
canonical-пути обязан быть correctly-rounded; печать точная ≠ roundtrip
точный»), а не заплатка, и правило записано так, что применимо к будущему
SVG-writer-у M2+.

### Прочие проверки, не давшие находок

- Порядок ключей JSON, целочисленная запись float, 1-ulp сдвиг — поведение
  корректно во всех трёх случаях (см. §3a).
- Реверсивная перенумерация, ротация loop-представителя, 100× повтор,
  debug vs release — детерминизм не сломан ничем из этого.
- 3000 кейсов на каждое свойство `canonical_props`, 20000 на каждое свойство
  `predicate_props` — падений нет.
- Паник нет ни в одном из ~25 сценариев; все отказы typed.
- Flaky-тестов нет (три полных прогона).

## 8. Замечания

### M1-N1 (блокирующее, корректность) — см. подробно §5

Непредставленный junction: две non-adjacent boundaries, касающиеся в точке,
совпадающей с interior-узлом цепочки, принимаются валидацией и не
регистрируются как undetermined. Причина — `validate.rs:665`, где смежность
определяется равенством позиций вместо тождества graph-вершин. Опровергает
G4 и утверждение STATUS_M1 «ТОЧНО для line-line пар»; противоречит
собственной формулировке ADR-0005 («с общей вершиной»). Исправление не
затрагивает golden-артефакт (0 коллизий в golden-сцене) и не требует
перезаписи ни одного записанного артефакта.

### M1-N2 (умеренное, документация + полнота): ADR-0007 переобещает охват политики

ADR-0007 п.1 утверждает: «Точка применения — одна: `exec::run_with_timeout`
(все build/run команды baseline-ов и selftest-adapter). Политика применяется
каждому ребёнку **без исключений**». Фактически политику **не** получают:

- `runner.rs:680` `git_output` — а через него `git clone`, `git checkout
  --detach`, `git rev-parse HEAD`, `git cat-file` (то есть весь
  provenance-путь);
- `runner.rs:257` — прямой `git cat-file` probe;
- `envinfo.rs:78` `tool_version` — probe версий `rustc`/`cargo`/`git`/`python`,
  результат которых попадает в `environment_sha256`.

Практического риска сегодня нет: удаляемый список состоит из
Rust/Cargo/Python-переменных, ни одна из которых не влияет ни на `git
rev-parse`, ни на `rustc -V`. Но утверждение «без исключений» фактически
неверно, а дыра станет реальной в тот момент, когда список пополнится
(например `GIT_*`, `GIT_CONFIG_GLOBAL`, или пиннинг `PATH`). Просьба: либо
применить `apply_child_env_policy` и в этих точках, либо переформулировать
ADR, назвав охват явно.

### M1-N3 (мелкое, точность отчётов): счётчики

- STATUS_M1 §2 и G4 называют `validate_rejects.rs` «38 негативных тестов».
  Фактически в файле 38 тестов, из которых **36 негативных**; `valid_scenes_pass`
  — позитивный контроль, `uncertified_pairs_are_reported_not_hidden` —
  позитивный + проверка отчётности. Разница не в пользу автора невелика, но это
  ровно тот класс неточности, за который REVIEW_M0 выставил N1.
- `THIRD_PARTY_NOTICES.md` §2a: колонка озаглавлена «Version (Cargo.lock)», но
  для `proptest` указано «1.x»; в `Cargo.lock` — `1.11.0`.
- `REQUIREMENTS_TRACEABILITY.md` M1-6 говорит «30+ негативных тестов» — здесь
  формулировка честная.

### M1-N4 (умеренное, дизайн артефакта): N3 не сдвинулся, а `environment_sha256` стал шире

Две связанные вещи.

1. C005 записал в `REPRODUCIBILITY_M0.md`, что разделение `hashes.json` на
   нормативную/информационную секции «запланировано на **M1**». В M1 оно не
   сделано; C009 переписал эту фразу, перенеся split на pre-M3 перезапись
   baseline-ов по B1/B2. Аргумент автора («менять схему artefact-файла без
   одновременной перезаписи записанных артефактов нельзя, а
   `docs/baselines/M0/**` неприкосновенны») — **корректен по существу**, и я
   его принимаю. Но это перенос срока, и он обязан отслеживаться явно, а не
   растворяться в правке одного абзаца.
2. Блок `command_env` (включая `ambient_overrides_present`) входит в
   `environment_sha256`. Следствие: две в остальном идентичные машины, у
   которых различается лишь **наличие** какой-нибудь `CARGO_INCREMENTAL`,
   дадут разные environment-хеши — хотя дети санируются одинаково и
   переменная доказуемо не может повлиять на результат. Аудит-ценность
   присутствия высокая, и я не предлагаю его убирать; предлагаю при
   pre-M3 перезаписи развести манифест на нормативную часть (политика,
   версии инструментов) и информационную (ambient presence) — это тот же
   N3-по-смыслу, и решать оба стоит одной правкой. Плюс: расширение схемы
   `env.json` в C009 означает, что побайтовая сверка `env.json` с записанным
   M0-артефактом теперь корректна только на коммитах C002–C005. Это
   **честно задокументировано** и в `envinfo.rs`, и в ADR-0007, и в
   `REPRODUCIBILITY_M0.md` — претензии к сокрытию нет, претензия к тому,
   что «исполнимость документированной сверки» после M1 стала не ближе, а
   дальше.

### M1-N5 (умеренное, отложенное): геометрическое вложение не проверяется

См. §5. Не gate-miss (список §12 выполнен буквально, ограничение
задокументировано), но обязано стать hard-проверкой в M2: signed-area
ориентация loops + принадлежность вложенных колец правильному face. Иначе
формулировка «invalid graphs rejected» навсегда сузится до
«комбинаторно невалидные графы отвергаются».

### M1-N6 (мелкое, наблюдение): geometry вне canvas не валидируется

Сцена целиком за пределами `[0,W]×[0,H]` проходит валидацию. §12 такого
инварианта не содержит, поэтому это не дефект — но политику (обрезка?
reject? предупреждение?) стоит выбрать осознанно в M2, до появления
renderer-а, а не по факту первого странного результата.

### M1-N7 (мелкое, качество тестов): один property-эталон не полностью независим

`orient2d` и `incircle` сверяются с **действительно независимой** exact-i128
реализацией (определитель, посчитанный из определения) — это сделано
правильно и это несущая часть. Но
`segment_intersection_matches_exact_reference` использует эталон
`exact_segments_intersect`, который структурно повторяет разбор случаев
самой библиотеки (те же четыре ориентации, те же четыре collinear-ветки,
тот же `opposite`), отличаясь только точной арифметикой. Такой эталон ловит
ошибку в **знаках**, но не поймает ошибку в **композиции** (например
пропущенную ветку) — она была бы продублирована в обеих реализациях. Для M1
это приемлемо (композиция дополнительно покрыта девятью ручными
unit-кейсами), но к M2, где §28 прямо требует «no self-reference-only
tests», эталон стоит переписать через независимую формулировку
(параметрическое решение / SoS), тем более что M1-N1 — это как раз ошибка
композиции, а не знаков.

### M1-N8 (мелкое, гигиена тестов): property-тест не масштабируется

`point_on_segment_is_exact` генерирует `k in 0..=1000`, `n in 1..=1000` и
затем отбрасывает половину входов через `prop_assume!(k <= n)`. При
`PROPTEST_CASES=20000` тест падает не по существу, а с «Test aborted: Too
many global rejects» (exit 101); с `PROPTEST_MAX_GLOBAL_REJECTS=200000` все
шесть свойств проходят. То есть **дефекта предикатов нет** — но тест нельзя
усилить, не настраивая харнесс, и половина его бюджета тратится впустую.
Генератор вида «`n in 1..=1000`, затем `k in 0..=n`» устранил бы и то, и
другое. §32 п.25 называет property-тесты обязательными, поэтому их
масштабируемость — не косметика.

### M1-N9 (информационное): формулировка принципа §32 п.7

См. §4. Сужение объёма признано законным. Но тем же тестом «нет call site»
можно было бы срезать `connectivity.rs` и большую часть `color.rs`, которые
автор (правильно) оставил. Стоит уточнить в ADR-0005, что критерий —
«принадлежит ли семантика типа текущему милестоуну», а не «есть ли
call site», иначе принцип выглядит применяемым избирательно.

### Что проверялось и НЕ дало находок

- Скрытые env-флаги — отсутствуют (§4); все три вхождения `env::var*`
  объяснены и безвредны.
- Копирование донорского кода — не обнаружено; независимый n-gram-скан по
  трём донорам (в т.ч. на пиннутых версиях) + ручное чтение всех файлов с

- Vendoring внешних crates — отсутствует; ни `vendor/`, ни source

## 9. Итоговая оценка

M1 по §28 требует: конвенции координат/цвета/топологии; типы exterior
face/DCEL; robust predicates adapter; типы geometry/paint/formation/hypothesis;
canonical shared-parameter сериализацию и digests. Gate: **property roundtrips,
same-platform byte determinism, invalid graphs rejected.**

**Что сделано хорошо — и это надо сказать прямо, потому что работа сильная.**
Канонический формат детерминирован не по совпадению, а доказуемо: тотальность
порядка следует из инвариантов, которые валидация уже проверяет, и я
подтвердил это и рассуждением, и четырьмя независимыми экспериментами, включая
полную реверсивную перенумерацию всех сущностей. Shared parameters сделаны
структурно неповторимыми, а не «запрещёнными к дублированию». Euler-проверка
**доказуемо** отвергает непланарные rotation systems, а не ловит их
эвристикой. Негативные тесты проверяют конкретный вариант typed-ошибки, а не
`is_err()`. Отказ F-0005 обработан образцово: пойман gate-тестом до коммита,
исправлен общим правилом, закреплён и property-seed-ом, и golden-байтами.
Механизм `uncertified_interference_pairs` — это редкий случай, когда система
материализует собственное незнание вместо того, чтобы его замолчать. Условия
REVIEW_M0 1–6 исполнены, 7 отслеживается; CI впервые зелёный на обоих
push-ах, и Linux-прогон дал побайтово тот же golden digest, что Windows —
результат сильнее, чем автор заявил. Следов копирования донорского кода нет,

### Проверка сути фикса (§9 п.1)

Принят вариант (b): новый инвариант `check_chain_point_distinctness` —
все точки цепочек (graph-вершины + interior-узлы всех цепочек) попарно
различны по позиции; typed-ошибка `UnrepresentedJunction { a, b:
ChainPointRef }` называет обе точки.

**Рассуждение ADR-0005 «позиция ≡ тождество ПОСЛЕ инварианта» я проверил
и считаю корректным.** Пусть `P` — множество точек цепочек. Инвариант даёт
`∀ p ≠ q ∈ P: pos(p) ≠ pos(q)`. Каждый `p0`/`p1` примитивного сегмента
берётся из `chain.node_positions(...)`, то есть является `pos(p)` для
некоторого `p ∈ P`. Следовательно равенство позиций в `shared_points`
влечёт тождество точки, и прежний позиционный тест смежности становится
точным, а не эвристическим. Две вещи, способные сломать вывод, проверены
отдельно: (1) **полнота** обнаружения коллизий — сортировка ведётся по
тотальному порядку (`lex_cmp`/`total_cmp`), поэтому равные позиции
гарантированно соседние, и скан `windows(2)` полон; (2) **порядок
проверок** — инвариант вызывается до `check_half_edges`/`check_euler`/
`check_segment_interference`, то есть предусловие на interference-этапе
выполнено. Обоснование выбора (b) над (a) в ADR также верно по существу:
(a) оставила бы совпадающие позиции легальными.

Формулировка ADR-0005 приведена в соответствие с кодом («общая **вершина**»
→ «общая **точка цепочки**»), как требовал §9 п.1.
