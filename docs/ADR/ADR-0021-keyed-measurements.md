# ADR-0021 — Ключ выводится из измерения: как PF10 стал вторым измеренным плечом

Дата: 2026-07-27. Милестоун: M4. Статус: принято.
Спека: §27.6, §28 M4; условия B1 и B2 из `docs/REVIEW_M3_5.md`.

## Контекст

M3.5 выразил §27.6 типом: `CausalDelta` с приватными полями и единственным
конструктором `CommensurableArms::contrast`. Ревьюер (M35-N3) показал предел
этого утверждения: `insert(arm, key, value, crime)` принимал ключ и значение
двумя НЕЗАВИСИМЫМИ аргументами, поэтому гарантия читалась как «вызывающий
предъявил один ключ», а не «операнды измерены в одних условиях». На
единственном продакшн-вызове множество создавалось из `key` и наполнялось тем
же `key`, то есть сравнение не могло сработать ни разу.

На M3.5 это ничем не эксплуатировалось: артефакт публиковал НОЛЬ дельт. M4
публикует второе плечо, поэтому условие B1 наступило.

## Решение

### Ключ — функция измерений

- `KeyedMeasurement` — то, что реализует измерение; `CeilingArm` несёт
  ЦЕЛИКОМ свой `CompatibilityKey`, а не только fingerprint;
- `FactorialArm::aggregate` ВЫВОДИТ ключ плеча из его членов: компоненты,
  которые обязаны совпадать, берутся из них (а член, который не совпал, —
  типизированный отказ с именем компонента), а fixture-компонент считается
  как хеш по собственным fixture-хешам членов, то есть является функцией
  ровно тех измерений, которые вошли;
- `CommensurableArms::new()` НЕ принимает ключ и усваивает ключ первого
  плеча, поэтому предъявить ключ больше негде;
- плечо над нулём измерений — отказ, а не ноль.

### Механизм окупился на первом же прогоне

PF10 и PF11 вышли над РАЗНЫМИ множествами фикстур: оценённая формация,
которую backend не может реализовать, даёт отказ, поэтому у PF10 меньше
членов. Выведенные ключи разошлись, и `insert` отказал. §27.6 требует, чтобы
плечи факториала делили фикстуры, поэтому факториал теперь идёт по
ПЕРЕСЕЧЕНИЮ и публикует, что отбросил: 376 пар оставлено, 380 отброшено.
Без вывода ключа две разные популяции усреднились бы молча.

### Что стало измеримым

`MissingCapability::FormationEstimation` УДАЛЁН, а не заполнен: M4 оценивает
формацию, поэтому у варианта, записывавшего её отсутствие, нет предмета.
PF10 = GT partition + ОЦЕНЁННАЯ формация измерен на реальных данных:

```text
1132 arm-а измерено, 380 отказано, 63 сцены
376 arms PF10 против 756 PF11
оценщик восстановил формацию ячейки на 198 из 376
254 отказа: оценщик не выдал формацию вовсе
126 отказов: оценка — ядро, которое backend не может реализовать
```

Отказ, а НЕ подстановка истины: подставить GT вместо провалившейся оценки
значит сделать PF10 копией PF11.

Все три эффекта по-прежнему отказ, владелец M4.5: контраст по половине
факториала — это та самая порядково-зависимая разность, которую §27.6
отменил.

### Ключ сдвинулся вместе с харнессом

`candidate_budget` стал `Exhaustive { formation_family: 8 }` там, где M3.5
имел `NotApplicable`: M3.5 не вёл поиска вовсе, M4 перечисляет семейство
исчерпывающе. Значит arm M3.5 и arm M4 НЕ соизмеримы — и это ключ,
выполняющий свою работу, а не версионная случайность.

Отсюда следует и судьба артефакта: `docs/gt/ORACLE_M3_5.json` не
воспроизводится кодом в дереве, а закоммиченный артефакт, который ничто не
может проверить, — ровно то, о чём был долг A7.2. Он удалён, его место занял
`docs/gt/ORACLE_M4.json` со схемой `m4-oracle/v1`; числа M3.5 остаются в
подписанных `STATUS_M3_5.md` и `REVIEW_M3_5.md`, которых M4 не трогает.

### B2: две вакуумные щели клаузы 2 закрыты

- `fold_all(∅) = Clean` пропускал агрегат БЕЗ arms: теперь число arms
  агрегата сверяется с числом реально совпавших, и пустое множество не
  проходит;
- `!warnings.is_empty()` принимал любую строку: теперь `warnings`
  сравнивается с МНОЖЕСТВОМ, выведенным из arms той же функцией, которая их
  произвела.

## Альтернатива, которая была отвергнута

Можно было оставить `insert(arm, key, value)` и добавить проверку «ключ равен
ключу измерения». Это тот же класс ошибки: проверка сравнивала бы то, что
вызывающий предъявил, с тем, что вызывающий предъявил. Разница между
«проверить» и «вывести» — и есть содержание M35-N3.

## Последствия

- любой будущий arm (PF00/PF01 в M4.5, G-лестница в M6) обязан прийти как
  `KeyedMeasurement`: другого пути к `FactorialArm` нет;
- отчёт публикует `assembly_refusals` — плечи, которые НЕ удалось собрать, с
  типизированной причиной; в здоровом прогоне список пуст, непустой означает,
  что два измерения, которые должны были делить ключ, его не делят.
