## 1. Методология

### 1.1 Изоляция

| Логи прогонов | `C:\Users\nirrt\AppData\Local\Temp\m2redh\out\*.log` |

`m2redh` — path-deps на `vice-geom` / `vice-ir` / `vice-render`, плюс скопированный test-support wiring helper (`src/scenebuild.rs`) как единственный заимствованный код: он строит half-edge-структуру из списка вершин/faces и **валидирует результат через `ValidatedScene::new`**, поэтому кривой фикстур падает громко, а не превращается в фальшивую находку.

Toolchain: pinned `1.96.0` (`rust-toolchain.toml`), x86-64 Windows 11. Профиль `dev` в харнессе имеет `overflow-checks = true` (как у `cargo test`), профиль `release` — `overflow-checks = false`, чтобы сравнивать поведение обоих.

### 1.2 Независимые эталоны

Ни один эталон не разделяет код с `vice-render`:

1. **Точное покрытие через клиппинг (`src/indep.rs`).** Полигон отсекается по каждому пикселю алгоритмом Сазерленда — Ходжмана по четырём полуплоскостям; знаковая площадь результата — это ровно `∫∫_pixel w dA` (для выпуклой области отсечения SH сохраняет функцию winding внутри). Алгоритмически это ДРУГОЙ метод, чем построчная трапецеидальная развёртка renderer-а.
2. **Суперсэмплинг winding.** 256×256 сэмплов на пиксель, winding считается crossing-count-ом. Третье, полностью независимое мнение (разрешение ~1e-5).
3. **De Casteljau** вместо бернштейновой формы `vice-geom` — для оценки истинной кривой при брутфорс-измерении хордового отклонения.
4. **Эллипсы из центральной параметризации.** Дуга строится по известным `center/rx/ry/φ/θ0/θ1`, во flattener подаются только endpoint-ы; отклонение меряется от *истинной* дуги, а не от того, что flattener сам себе считает истиной.
5. **Translation oracle (для больших координат).** Фигура кладётся на смещение `base = 2^k`; ground truth — та же фигура, сдвинутая на `−base`. Вычитание `x − base` **точно** (лемма Стербенца при `base ≤ x ≤ 2·base`), поэтому «маленькая» копия геометрически тождественна большой бит-в-бит, а её рендер имеет ошибку ~1e-16 и служит эталоном. Это обходит проблему, что f64-эталон при координатах 1e7 сам хуже, чем объект суда.

## 3. Найденные проблемы

### F-M2-R1 — MAJOR. Арифметическое переполнение в `subdivisions_for_quadratic_decay`: panic вместо typed error на ВАЛИДНОЙ сцене; debug ≠ release

**Место.** `crates/vice-geom/src/flatten.rs:110`

```rust
fn subdivisions_for_quadratic_decay(k: f64, tol: f64) -> u32 {
    if k <= tol { return 1; }
    let n = (k / tol).sqrt().ceil() as u32 + 1;   // <-- строка 110
    n.clamp(1, MAX_SUBDIVISIONS)
}
```

Каст `f64 → u32` в Rust **насыщающий**: при `sqrt(k/tol) ≥ u32::MAX` он даёт `4294967295`, после чего `+ 1` переполняется.

**Порог (аналитический и подтверждённый бисекцией, 60 итераций).**

```
k > u32::MAX² · tol = 2.882304e17           (при tol = 1/64)
|p0 − 2c + p1| > 1.152922e18                (quad)
для ctrl=(m,m), p0=(0,0), p1=(1,0):  m > 4.076193e17
эмпирическая граница: ok при 4.076193e17, panic при 4.076193e17 (соседние f64)
```

**Репро (полный, через типизированный `ValidatedScene`).**

```rust
let mut raw = wire_scene_raw(64, 64,
    &[Pt::new(10.0,10.0), Pt::new(50.0,10.0), Pt::new(30.0,40.0)],
    &[transparent(), red()],
    &[ BoundarySpec { start:0, end:1, left:1, right:0,
         chain: CurveChain::single(Segment::Quad{ ctrl: Pt::new(30.0,-20.0) }) },
       line(1,2,1,0), line(2,0,1,0) ]);
// подменяем контрольную точку УЖЕ после разводки, чтобы тестовый helper не был объектом атаки
raw.graph.boundaries[0].curve.segments[0] = Segment::Quad { ctrl: Pt::new(1e19, 1e19) };

let v = ValidatedScene::new(raw).expect("валидируется");   // <-- проходит
render_partition(&v, &RenderOptions::default());
```

**Факт (наблюдено, `out/r3.log`):**

```
scene with quad ctrl 1e19 VALIDATES as a ValidatedScene
  [release] render: typed error -> tessellation budget exceeded at boundary BoundaryId(0)
            segment 0: certified 7071067811865617000 px > requested 0.015625 px (subdivision cap)
  [debug]   render: PANIC (arithmetic overflow in flatten.rs:110)
```

**Почему это находка.**

1. Сцена **валидна**: все числа конечны, `-0.0` нет, §12-инварианты выполнены. `check_numbers` не ограничивает магнитуду; `check_segment_params` для `Quad` — безусловный `Ok(())`. Control point за пределами canvas ЯВНО легитимен по ADR-0009 п.2 («Bézier control points законно выходят за canvas»).
2. Модуль-документация `validate.rs` гласит: «An invalid scene is a TYPED reject, **never a panic**». Здесь сцена даже не invalid, а panic всё равно есть.
3. **Один вход — два разных исхода** в зависимости от профиля. Профиль `dev` (overflow-checks on) — это ровно то, чем проект гоняет свой gate (`cargo test`). То есть в конфигурации gate-а renderer аварийно завершает процесс на классе валидных сцен.

**Тот же паттерн — во второй функции.** `arc_subdivisions` (`flatten.rs:265`) содержит `(sweep_abs / phi_max).ceil() as u32 + 1`. Достижимого входа я **не нашёл**: при `tol/r < ~1.1e-16` выражение `1.0 - tol/r` округляется ровно в `1.0`, `acos(1.0) = 0`, и ветка `phi_max <= 0.0` уводит в `MAX_SUBDIVISIONS` раньше переполнения. Отмечаю как латентный, не как подтверждённый.

**Что чинить (общее, не заплатка).** `f64 → u32` с последующей арифметикой — целый класс. Правильная форма: считать в `f64`, клампить ДО каста (`(ratio + 1.0).min(MAX_SUBDIVISIONS as f64) as u32`), и добавить property-тест «flatten никогда не паникует на любых конечных входах» в обоих профилях. Отдельно: `check_segment_params` для Bézier сегодня не проверяет ничего — стоит решить, есть ли у сцены домен по магнитуде координат (см. также F-M2-R3).

### F-M2-R2 — MAJOR. Типизированный допуск 1e-9 не обоснован на диапазоне canvas, который сам код разрешает; ошибка возвращается молча и структурно невидима partition-checker-у

**Заявления, которые атакуются.**

- `partition.rs`, doc `PartitionTolerances`: «For canvases **up to 2^12 px** and thousands of edge pieces per row the accumulated absolute error stays below ~1e-11; both tolerances are frozen at 1e-9 — two orders of margin».
- ADR-0010 «Resource limit»: `MAX_COVERAGE_ELEMENTS = 2^27` (faces × W × H). При двух faces это допускает **ширину до 2^26**.
- F-0006 (2): «для произвольных координат утверждается только typed bound (**≤1e-12 на пиксель**), тоже тестом» — тест `integer_translation_shifts_general_coverage_within_float_noise` в `coverage.rs` ассертит `<= 1e-12`.

**Между 2^12 и 2^26 не стоит НИЧЕГО.** Домен обоснования нигде не проверяется.

**Причина.** В `coverage.rs::emit_row_pieces`:

```rust
area[ci] += dy * ((x0 + x1) / 2.0 - c as f64);
```

`x0, x1 ∈ [c, c+1]`, но сумма `x0 + x1` вычисляется **до** вычитания `c`. При `c ~ 2^k` величина `x0+x1 ~ 2^(k+1)`, и полуулп её округления равен `2^(k+1)·2^-53`. Для осевых рёбер срабатывает быстрый путь `sx == ex` (там `(sx+sx)/2 = sx` точно, а `sx − c` точно по Стербенцу) — поэтому эффект не виден на прямоугольниках, на которых написан in-tree тест. Он проявляется только на **наклонных** рёбрах.

**Измерения (translation oracle, `out/n1f.log`).** Одна и та же фигура (недиадическая, наклонная, 4 вершины) на смещении `2^k`; ground truth — она же при `x − 2^k` (вычитание точное):

|---|---|---|---|---|

| 2^10 | 1 056 | 1.393e-13 | ok | ok |
| 2^12 | 4 128 | 7.043e-13 | ok | ok |
| **2^13** | **8 224** | **1.271e-12** | **ПРЕВЫШЕН** | ok |
| 2^14 | 16 416 | 2.505e-12 | ПРЕВЫШЕН | ok |
| 2^16 | 65 568 | 4.542e-12 | ПРЕВЫШЕН | ok |
| 2^18 | 262 176 | 4.345e-11 | ПРЕВЫШЕН | ok |

**Полный сертифицированный рендер это НЕ ловит (`out/n1h.log`).**

```
canvas 16777248x2, 2 faces = 67108992 coverage elements (renderer limit 134217728)
  ACCEPTED (no typed error) in 976.5914ms
  worst per-pixel coverage error vs the same shape at the origin = 6.7934e-10
      (renderer 0.11215555599614505 vs ground truth 0.11215555531680593, pixel c=0,r=0)
  worst |sum - 1| over the same pixels = 0.0000e0
```

**Ключевой момент — почему checker слеп.** Ошибка **common-mode**: shared polyline обходится двумя faces с противоположным знаком `dy` и теми же `x0, x1`, поэтому член `dy·((x0+x1)/2 − c)` сокращается **бит в бит**. `PartitionSumViolation` не сработает никогда — `worst |sum−1| = 0.0`. `PartitionRangeViolation` тоже не сработает: полностью покрытые пиксели получают вклад из full-cover bucket ровно `1.0`, а ошибка живёт только в частично покрытых, где значение заведомо < 1. То есть **оба типизированных стража конструктивно не видят этот класс ошибок**, и неверное значение возвращается молча.

**Репро.** `m2redh n1f` и `m2redh n1h`.

**Что чинить.** Три опции, любая — reviewed-решение, а не расширение порога:
1. Ввести типизированный домен: max ширина/высота canvas и/или max магнитуда координат, `CanvasTooLarge`-подобный typed reject за его пределами; поднять его до уровня `ValidatedScene`, а не только `MAX_COVERAGE_ELEMENTS`.
2. Сделать допуск функцией магнитуды: `tol = max(1e-9, C·ulp(2·W))`, с выведенной константой.
3. Убрать источник: считать `x0 - c` и `x1 - c` **до** усреднения (обе разности точны по Стербенцу), т.е. `dy * (((x0 - cf) + (x1 - cf)) / 2.0)`. Это дешёвая и, судя по природе ошибки, полностью устраняющая правка — но её надо доказать, а не «попробовать».

Отмечу честно: при `W ≤ 2^12` (документированный домен) всё точно как заявлено. Находка — в том, что домен **не выражен в типах и не проверяется**, а F-0006 (2) падает уже на 8192 px — совершенно рядовой ширине.

### F-M2-R3 — MAJOR. Стоимость рендера линейна по МАГНИТУДЕ КООРДИНАТ, не по W×H; типизированного предела нет

**Место.** `coverage.rs::emit_row_pieces` идёт по ячейкам **по одной**:

```rust
let mut c = sx.floor() as i64;
let c_end = ex.floor() as i64;
...
while c < c_end { ...; c += 1; }
```

Цикл проходит **все** колонки между `floor(sx)` и `floor(ex)`, включая колонки далеко за пределами canvas (где `emit` лишь складывает `dy` в один full-cover bucket). Ранний выход из «зоны вне canvas» отсутствует.

**Измерения (release, canvas 16×16, ОДИН треугольник, `out/r1.log`).**

| дальняя вершина x | время |
|---|---|
| 1e2 | 9.4 µs |
| 1e3 | 7.2 µs |
| 1e4 | 54.5 µs |
| 1e5 | 590.6 µs |
| 1e6 | 5.381 ms |
| 1e7 | 54.063 ms |
| 1e8 | 537.525 ms |
| 1e9 | **5.364 s** |

Идеальная линейность (×10 координата → ×10 время). Экстраполяция: 1e12 ≈ 1.5 часа, 1e15 ≈ 62 суток, 1e18 ≈ 170 лет. Валидация допускает любое конечное f64 (до ~1.8e308) — `check_numbers` проверяет только `is_finite` и `-0.0`.

**Что именно опровергнуто.** ADR-0009, «Последствия»:

> «Renderer никогда не аллоцирует буферы по экстенту геометрии — только по canvas: resource-bound по W×H (ADR-0010), **независимо от координат сцены**.»

Для **памяти** — верно (проверено: буферы 16×16 при координате 1e9). Для **времени** — неверно: время Θ(экстент геометрии). Формулировка «resource-bound по W×H» без квалификатора это скрывает. Также нарушен принцип, который сам код цитирует в `MAX_COVERAGE_ELEMENTS` («explicit resource limits» линии M0) и §29 «no uncontrolled growth», на который ссылается `MAX_SUBDIVISIONS`.

**Классификация.** Это не «молча неверный пиксель» — результат при 1e9 корректен (`clipped_sum = 148.499999`, аналитически 148.5). Это отказ в обслуживании на валидном входе без типизированного предела: рендер просто не завершается, и ни одна typed-ошибка об этом не сообщает. По моей шкале — MAJOR, требует решения до M3.

**Что чинить.** Клампить пробег по ячейкам к `[-1, W]` до цикла: колонки `c < 0` не вносят ничего, колонки `c ≥ W` вносят суммарно `dy` в один bucket — обе группы вычисляются в O(1) без итерации. Плюс отдельно решить, есть ли у сцены типизированный домен координат (см. F-M2-R1).

### F-M2-R4 — MINOR. Заявление F-0006 (1) о битовой инвариантности на диадической решётке ложно

**Заявление.** FAILURE_LEDGER F-0006, «Исправление»: «(1) битовая инвариантность утверждается и тестируется **на диадических координатах**». In-tree тест: `coverage.rs::integer_translation_shifts_dyadic_coverage_bitwise`.

**Контрпример (`out/n3b.log`).** Треугольник, ВСЕ координаты — n/8 (диадические, k = 3):

```rust
let tri = [Pt::new(1.25, 1.125), Pt::new(9.75, 4.375), Pt::new(3.5, 8.625)];
```

| сдвиг | пикселей, различающихся ПОБИТОВО | max \|Δ\| |
|---|---|---|
| (+3,+2) | **18** | 4.996e-16 |
| (+5,+3) | 17 | 4.441e-16 |
| (+1,+0) | 3 | 4.441e-16 |
| (+0,+1) | 7 | 3.886e-16 |
| (+4,+4) | 17 | 4.441e-16 |

Пример: пиксель (1,1) при сдвиге (+3,+2): `0.43386948529411751` vs `0.43386948529411801`.

**Контроль в том же прогоне:** осевой диадический прямоугольник (ровно форма in-tree теста), сдвиг (+5,+3) → **0 различающихся пикселей**. То есть тест зелёный не потому, что заявление верно, а потому, что фикстур принадлежит подклассу, где верно.

**Причина.** `emit_row_pieces`:

```rust
let y_of_x = |x: f64| sy + (x - sx) * dy_dx;
```

Для осевого ребра `sx == ex`, срабатывает быстрый путь, `y_of_x` не вызывается вовсе. Для наклонного — вызывается, и финальное сложение `sy + u` переокругляется при сдвиге `sy` на целое, даже когда `sy`, `u` и `dy_dx` диадические (сумма может потребовать больше 53 бит мантиссы, чем слагаемые по отдельности).

**Почему MINOR, а не MAJOR.** Численного вреда нет: 5e-16 на 3 порядка внутри общего typed bound 1e-12 и на 6–7 порядков внутри enforced 1e-9. Ломается **класс входов в заявлении**, а не число. Но именно это F-0006 и вынес как правило: «Любое заявление о битовом равенстве f64-вычислений обязано указывать класс входов, на котором арифметика точна». Правило записано верно — применено неточно.

**Что чинить.** Либо сузить заявление до фактически доказуемого класса («диадические координаты **при осевых рёбрах**», т.е. когда не происходит y-интерполяция), либо перевести весь диадический случай в typed bound. И расширить сам тест на неосевой диадический полигон — иначе класс так и останется непроверенным.

## 4. Что сломать НЕ удалось (честно)

Перечисляю с числами, потому что «не сломалось» без чисел ничего не стоит.

**Сертифицированный tessellation budget — выдержал полностью.** 24 брутфорс-случая Bézier плюс 12 дуг плюс 8 эллипсов, по 200 000–400 000 сэмплов на кривую, независимый эвалюатор (de Casteljau) и независимая метрика (проекция точка-отрезок). **Ни одного превышения.** Специально пробовал: почти-касп (`cubic_near_cusp`), точный касп, самопересекающуюся петлю, control point на 1e5 при хорде 1, координаты 1e8, дугу с r = 1e9 (где `sqrt(r² − half²)` катастрофически теряет точность — покрыто eval-guard-ом: certified 2.88e-5 против measured 3.79e-7), почти-полный оборот (sweep 2π−1e-7), и вырожденные эллипсы вплоть до `ry = 1e-12` при `rx = 50`. Последнее — самая перспективная на бумаге атака: `to_circle` делит на `ry`, параметризация действительно разрушается (`|r_unit − 1|` доходит до 6.2e-3), но `from_circle` умножает обратно на `ry`, и обусловленность **восстанавливается**; измеренное отклонение 7.1e-15 против заявленных 1.44e-2. Замечу для протокола: при таком вырождении сохраняется *форма*, но не *параметризация* — точки могут идти по кривой не монотонно. На бюджет это не влияет (Хаусдорф двусторонне мал), но если M6 начнёт полагаться на монотонность параметра вдоль polyline, это отдельный вопрос.

**Партиционные инварианты — выдержали.** Сетка 1601 face на canvas 64×64: worst `|sum−1|` = **2.22e-16**. Фаззинг 4000 случайных сцен: то же 2.22e-16, ноль NaN. Triple junction: доли складываются напрямую, расхождение с независимым эталоном **0.0 точно**. Разрез фигуры на две части против целой: **Δ = 0.0**.

**Суд независимых эталонов — подтвердил renderer.** Два независимых метода (SH-клиппинг и суперсэмплинг 256×256) против `vice-render` на 7 сценах, 348 672 сравнений пиксель×face: max |Δ| = **1.95e-13**, mean ≤ 1.9e-15. На 20 000 случайных полигонов: 1.87e-13. Пороги ADR-0012 (0.17 / 0.30 / 0.02) не приближены на 10+ порядков. Мой суд принципиально острее внешних растеризаторов, потому что не ограничен 8-битной альфой — и всё равно расхождения нет.

**ROI — бит-в-бит, без исключений.** 9216 окон 1×1 (все пиксели четырёх сцен 48×48), все краевые/угловые/полнострочные/полностолбцовые окна, перекрывающаяся черепица 7×7 с шагом 4 — **0 несовпадающих битов** и по `face_coverage`, и по `composite`. Специально включал сцену со срезанной границей canvas (`straddling`) и сцену с кривыми (`curveblob`). Заявленный dependency closure (row band на полной ширине) выполняется буквально.

**Детерминизм — выдержал всё.** 100 повторов × 5 сцен → 1 digest на сцену, причём digest считался не только по composite (где прозрачные faces невидимы), но и по **всем** значениям `face_coverage`. 5 release-процессов + 3 debug-процесса → все восемь наборов идентичны, включая debug↔release. Seal-цикл 50 повторов × 4 сцены → 1 distinct. Сдвиг вершины на 1/2/8/1024 ulp: каждый даёт РОВНО один digest (20 повторов), все четыре отличаются от базового — то есть чувствительность предсказуемая, а не «иногда».

**Порядок элементов — не влияет.** Ротация стартовой вершины loop-а: 0 различающихся пикселей, побитово.

**Clip-политика ADR-0009 — согласована.** 9 краевых конфигураций (включая canvas 1×1 и фигуру ровно по границе): worst `|sum−1|` = **0.0** везде, клиппированные площади точны.

**Embedding certification — честна на грани.** Кольца с signed area → 0: принимаются с верной площадью до eps = 1e-12, при 1e-14 — типизированный `UncertifiableLoopOrientation` с явными числами (|area| 4.5e-13 против certified 1.1e-11). Тонкие полумесяцы — типизированный отказ. Молчаливой неверной классификации не найдено ни разу. Побочное наблюдение (не находка): certified area bound = Σ(2δ·|chord| + 4δ²) очень консервативен — при δ = 1/64 face с периметром P не сертифицируется, если её площадь ≲ P/32 px². Это отказ в безопасную сторону, но означает, что мелкие детали требуют явного ужесточения бюджета; стоит это где-то записать.

**Топология.** Самопересекающийся cubic как граница face → `PartitionRangeViolation` (coverage 1.0462). Два острова, пересекающиеся из-за выпирающего Quad → отказ вплоть до перекрытия 1.4e-2 px; ниже этого тесселированные границы **действительно** не пересекаются (дефицит хорды ≈ chord tolerance 1/64), так что принятие — прямое следствие задокументированного бюджета, а не скрытая ошибка. Hairpin с зазором до 1e-12 px — корректная площадь. Ни одного молчаливого неверного результата.

**Чего я НЕ проверял (границы этого прохода).**
- Только x86-64 Windows, rustc 1.96.0. Кросс-платформенная стабильность digest-ов (libm `sin/cos` для дуг, уже исключённых из замороженных артефактов по ADR-0008 §8) не проверялась.
- Canonical-сериализация и внешние растеризаторы суда (`tiny-skia`, `raqote`) — вне моего мандата; они покрыты in-tree gate-ом.
- Мой f64-эталон разрешает ~1e-13 на canvas-масштабе; для больших координат я поэтому переключался на translation oracle, а не на клиппинг. Строки `canvas_w=...` в `out/n1.log` меряли ошибку **моего** эталона, а не renderer-а — авторитетны только числа N1f/N1h.
- Concurrency не атаковалась: в crate нет потоков и hash map по построению (проверено чтением).

### Что закрыто и что нет

**Закрыто полностью:** F-M2-R1, F-M2-R3, F-M2-R4, F-M2-R5, F-M2-R6. По каждой я строил репро заново, а не сверялся с отчётом; по R1 и R3 — в обоих профилях.

**F-M2-R2 — закрыта в объявленной автором форме, и автор честен насчёт остатка.** Внутри enforced-домена мне не удалось приблизиться к границе: 7.46e-13 при выведенной 2.33e-10. Вне домена система теперь отказывает типизированно на всех трёх путях. Утверждение «закрыт домен, а не число» — точное. Заявленная редукция «вдвое» подтверждена по порядку (я мерю 1.3–3.1× на разных магнитудах, 1.30× на 2^24), закон ulp(M) подтверждён численно. Единственная поправка — F-M2-R10 ниже.

**Побочно подтверждено (не находки):** порог обнаружения геометрического перекрытия кривых по-прежнему ≈ chord tolerance 1/64 (перекрытие 1.4e-2 отвергнуто, 1.0e-2 принято) — прямое следствие задокументированного бюджета; внешние судьи по-прежнему разрешают только грубую ошибку — так и написано в модуле.

### Новые находки

**F-M2-R7 — MAJOR. Не-конечный вход в типизированный публичный `polygon_coverage`: паника в debug против молчаливого NaN в release.**

```rust
let lp = vec![Pt::new(2.0,2.0), Pt::new(f64::NAN,4.0), Pt::new(6.0,6.0), Pt::new(2.0,2.0)];
polygon_coverage(&[&lp], 8, 0, 8)
// release: Ok(..)  -> 4 NaN-пикселя, sum = NaN, НИ ОДНОЙ ошибки
// debug:   panicked at crates/vice-render/src/coverage.rs:226:13
//          "cell piece must lie inside its own column"
```

То же для `+inf` (2 NaN-пикселя) и `-inf` (1). `CoverageError` перечисляет `UnclosedLoop`, `DegenerateLoop`, `InvertedRowBand` — но не конечность.

Почему MAJOR, а не гигиена:

1. **Это регрессия, внесённая самой починкой.** До дельты оба профиля молча возвращали NaN. `debug_assert` в `emit` (C032) создал расхождение «один вход — два исхода» — ровно тот паттерн, ради которого написано правило F-0007, и ровно вопрос (в) из задания. Ответ: да, новый `debug_assert` стал источником debug/release расхождения.
2. **Нарушено собственное правило дельты F-0011** («предусловия публичного API принадлежат типу или typed-ошибке — никогда debug-only проверке»), причём новым кодом той же дельты. Починка закрыла два предусловия, которые red team назвал поимённо, и пропустила третье того же класса.
3. Release-исход — не «мусор», а **NaN без ошибки**: он распространится в любой downstream-буфер.
4. Property-тест тотальности, найденный в C031, покрывает `flatten`; у `coverage` аналога нет.

**Ограничение области поражения (заявляю явно):** через `ValidatedScene`/`render_partition` это НЕ достижимо — `check_numbers` запрещает не-конечные числа, а `NumericDomain::contains_coord` независимо требует `is_finite`. Ни одно отрендеренное изображение не затронуто. Риск — прямые вызовы публичного аккумулятора, а первые такие потребители появляются в M3 (`vice-image`/`vice-cli`). Отсюда «фикс до M3». Фикс — одна проверка `is_finite` в том же цикле, который уже проверяет замкнутость, плюс вариант `CoverageError::NonFinitePoint`.

**Третьей дыры класса «насыщающий каст / переполнение» на пути flatten→mesh→coverage я не нашёл.** Проверено: оба места `piece_count_from_estimate` (включая `arc_subdivisions`, где вход недостижим), новая проверка конечности центра дуги, `sx.floor() as i64` при 1e300 (насыщается в i64::MAX → корректная ветка bucket), `NaN.floor() as i64` (даёт 0 — именно этот путь и приводит к F-M2-R7), `width_px = 0`, субнормальные dy с огромным dx (`inv_dy = ±inf` — результат остаётся конечным и корректным), 200 000 фаззинг-случаев в debug.

**F-M2-R8 — MINOR. SH-арбитр суда несостоятелен на объявленном численном домене.**

Суд называет SH-эталон «exact up to f64» и ассертит `|renderer − SH| ≤ 1e-12` как **первичную** сертификацию, а ADR-0012 строит на нём правило арбитража («если эталон согласен с vice-render — находка против СУДЬИ»). Измерено (ground truth — translation oracle):

| M | ошибка SH-арбитра | ошибка renderer-а | \|ours−SH\| | assert 1e-12 |
|---|---|---|---|---|
| 2^8 | 1.15e-13 | 2.84e-14 | 1.16e-13 | ok |
| 2^10 | 7.92e-13 | 6.52e-14 | 7.95e-13 | ok |
| 2^12 | 1.29e-12 | 2.68e-13 | 1.36e-12 | **сработает** |
| 2^13 | 4.64e-12 | 4.35e-13 | 4.55e-12 | **сработает** |
| **2^14** (= `max_canvas_dim_px`) | **1.01e-11** | **1.38e-12** | 1.09e-11 | **сработает (11×)** |
| **2^16** (= `max_abs_coord_px`) | **3.20e-11** | 4.54e-12 | 3.19e-11 | **сработает (32×)** |

Арбитр в 7.3× менее точен, чем подсудимый, ровно на границе объявленного домена. Сегодня gate зелёный только потому, что весь committed-набор ≤ 49 px. Любая сцена с координатами ≳2^12 даст **ложный FAIL против корректного renderer-а**, а правило арбитража ADR-0012 при этом обвинит не ту сторону. Причина — та же, что я нашёл у себя: shoelace считается в абсолютных координатах (члены порядка M², при M=2^14 это ulp(2.7e8) ≈ 6e-8) и отсекаемая координата местами интерполируется. Фикс тот же и дешёвый: перенос клиппированного полигона в начало пикселя перед shoelace (перенос точен по Стербенцу). У меня это переместило эталон с 1e-7 на 1e-16. Нужно либо это, либо явно записать, что домен валидности арбитра ≈2^11 и он уже, чем `NumericDomain`.

**F-M2-R9 — MINOR. Пара «допуски ↔ домен» не связана типами.**

`RenderOptions { budget, tolerances, domain }` — все поля публичные и независимые; `PartitionTolerances::for_domain` есть, но ничто не обязывает им пользоваться. Через публичный API тривиально воспроизводится ровно ситуация F-M2-R2:

```rust
let wide = NumericDomain { max_abs_coord_px: 4.0*2f64.powi(24), max_canvas_dim_px: 1<<15 };
RenderOptions { tolerances: PartitionTolerances::default(), domain: wide, .. }
// domain.coverage_error_bound_px() = 2.38e-7, а объявленный допуск остался 1e-9
// фактическая ошибка покрытия на |x| = 2^24: 1.33e-9  -> 1.3x сверх объявленного
```

ADR-0013 утверждает «a tolerance is only meaningful together with the domain it was proven on». Тип это не обеспечивает — обеспечивает только дисциплина вызывающего. Достаточно приватизировать поле `tolerances` и выводить его из `domain` в конструкторе (или сделать `RenderOptions::for_domain`).

**F-M2-R10 — MINOR. Заявление «остаток — предел представления, а не алгоритма» — переформулировка сверх доказуемого.**

`coverage.rs` пишет: «The residual magnitude dependence is NOT in the integration but in the geometry itself... That is a property of f64, not of this algorithm». Это верно для позиций **вершин** полилинии, но остаток, который реально измеряется, вносит **промежуточная** интерполяция `x_at(y) = xlo + (y−ylo)·inv_dy` в `accumulate_edge`: результат хранится в абсолютных координатах и потому квантуется шагом ulp(M). Прямой замер (200 000 точек по y на каждой магнитуде):

```
M=2^16: max |via_magnitude_M − column_relative| = 7.267e-12 = 1.00 x ulp(M)/2
M=2^20: 1.162e-10 = 1.00 x ulp(M)/2
M=2^24: 1.860e-9  = 1.00 x ulp(M)/2
```

То есть та же колонко-относительная перестановка, которая закрыла F-M2-R2 в `emit_row_pieces`, применима на уровень выше — в `accumulate_edge`, — и снимает остаток ещё раз. Практических последствий внутри домена нет (при M=2^16 остаток 4.5e-12 против границы 2.33e-10, запас 50×); это точность формулировки, и по духу F-0006 её стоит поправить: «предел выбранного представления промежуточной позиции», а не «предел f64».

### Наблюдения без классификации

- `check_numeric_domain` обходит `boundary_polylines`, а `face_coverage_band` читает `face_loops`. Отравление только `face_loops` (публичные поля `RenderMesh` + публичный `render_mesh_partition`) домен-проверку минует, но перехватывается ниже — `verify_embedding` для NaN/inf и partition-sum для 1e12, **одинаково в обоих профилях**. Не эксплуатируется, но проверка не покрывает поля, которые реально читает потребитель.
- `edge_mean` выбирает знаменатель по НАШЕМУ значению, поэтому дефект, выталкивающий пиксели из (0,1), уменьшает и числитель, и знаменатель: подогнанное «насыщение хвостов» даёт max 0.21 / edge_mean 0.00 — оба под порогами. Это не находка (SH-плечо на 1e-12 ловит всё, и разделение ролей задокументировано), но вместе с F-M2-R8 означает, что на большой сцене оба плеча суда ослепли бы одновременно.

- F-M2-R7 (MAJOR) — non-finite input to the typed public `polygon_coverage`: debug panics at the new `debug_assert` (`coverage.rs:226`) while release returns a NaN buffer with no error; a debug/release divergence introduced by C032 and a violation of the delta's own F-0011 rule. Not reachable through `ValidatedScene`/`render_partition`; blast radius is direct callers of the accumulator, which M3 introduces.
- F-M2-R8 (MINOR) — the court's SH arbiter is up to 7.3x LESS accurate than the renderer at the declared domain edge; its `<= 1e-12` assert starts firing against a correct renderer from M ~ 2^12.
- F-M2-R9 (MINOR) — `RenderOptions.tolerances` and `.domain` are independent public fields; F-M2-R2 is reproducible through the public API (1.33e-9 against a declared 1e-9).
- F-M2-R10 (MINOR) — "the residual is a property of f64, not of this algorithm" overstates: the intermediate interpolated position is stored in absolute coordinates and the column-relative form differs by exactly ulp(M)/2.

Closed and verified independently in both profiles: F-M2-R1, F-M2-R3, F-M2-R4, F-M2-R5, F-M2-R6. F-M2-R2 closed within the enforced domain (worst measured 7.46e-13 against a derived bound of 2.33e-10), with the author's own statement of its incompleteness confirmed as accurate.
